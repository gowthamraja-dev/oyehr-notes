# 210 — Fix three migration defects that break a fresh database (prod)

## Background
hrms-dev was patched by hand, so three migration problems never showed up there. Every one
of them breaks `scripts/migrate.py upgrade heads` on an empty database, which is what prod
(RDS) and any fresh environment will run. Reported by the team lead. Goal: **the smallest
change that lets a fresh DB migrate to head, while hrms-dev stays a no-op.**

**Built in the top-level `hrms/` clone** (user's call, 11-Oct-26), on branch
`bugfix/gowtham_FreshDbMigrations` cut from `origin/main` (`800f3ed`). Not workspace-2.

### Why editing applied migrations is OK here
CLAUDE.md says never hand-edit an applied migration. This is a deliberate, narrow exception:
the edits only add existence guards or rename an index *inside a table-exists guard*. On
hrms-dev, Alembic has already passed these revisions and never re-runs them, and even if it
did the guards would make them no-ops. The resulting schema on a fresh DB is the same as
dev's. Say this in the commit message.

## Scope

### 1. `a2b0363dc35a` (CR-008 departments): guard the autogenerated "drift" section
File: `backend/alembic/versions/a2b0363dc35a_cr_008_add_department_module_with_multi_.py`,
`upgrade()` only, lines ~102–155 (from `op.drop_constraint(op.f('payroll_employee_payslips_payslip_number_key')`
to `# ### end Alembic commands ###`). Autogenerate diffed against hand-patched dev, so this
section drops indexes and constraints that only exist on dev and re-creates ones an earlier
migration (`001_add_rbac_tables`, `003_add_visitor_management_tables`, …) already built.
My count: 23 `drop_index`, 4 `drop_constraint`, 24 `create_index`, 3 `create_unique_constraint`.
(The report said 26/3/23/3. It doesn't matter, because every line in the section gets guarded.)

Alembic is 1.18.5 (`uv.lock`), so do it with keyword args rather than raw SQL:
- `op.drop_index(..., if_exists=True)` on all 23
- `op.create_index(..., if_not_exists=True)` on all 24
- `op.drop_constraint(..., if_exists=True)` on all 4
- `create_unique_constraint` has no `if_not_exists`. Wrap the 3 calls (`uq_visit_number_per_cdp`,
  `uq_visitor_code_per_cdp`, `uq_pass_number_per_cdp`) in a small `_has_constraint(table, name)`
  check, using the inspector helper from `c4f1a9d2e7b8` (`sa.inspect(op.get_bind()).get_unique_constraints(table)`).

Leave the three `department_*` table creates and their indexes alone; those tables are new
in this revision. Also leave `downgrade()` alone. It's out of scope (nobody downgrades
past CR-008), so add a single comment noting that it isn't fresh-DB-safe.

### 2. `c4f1a9d2e7b8` (mobile punch verification): shorten one index name
File: `backend/alembic/versions/c4f1a9d2e7b8_mobile_punch_verification.py`.
`ix_work_location_network_details_care_delivery_program_master_id` is 64 chars, and
PostgreSQL / SQLAlchemy cap identifiers at 63. Rename it to
`ix_work_location_network_details_cdp_id`. Nothing else changes.
- It sits inside `if not _has_table("work_location_network_details")`, so dev, where the
  table already exists, is unaffected.
- The model (`app/models/work_location_network_detail.py:36`) uses `index=True`, which
  produces the long name. Don't change the model in this task. The only effect is that a
  future autogenerate may suggest renaming this index, and the reviewer should drop that line.
- Leave the 7 other long names in older migrations alone. They go through `op.f()` and are
  truncated automatically.

### 3. New migration: add `users.last_activity_at`
`app/models/user.py:62` declares it and `app/modules/auth/service.py` (~608–720) reads and
writes it on every login and authenticated request. However, no migration creates it. The
only `last_activity_at` in migrations belongs to `message_transaction_details`
(`d4ba88fd4eff`). Without the column, every login on prod fails.
- Hand-write it (don't autogenerate, because dev drift would add unrelated ops), and follow the
  style of `c4f1a9d2e7b8`, including the `_has_column` helper:
  ```python
  if not _has_column("users", "last_activity_at"):
      op.add_column("users", sa.Column("last_activity_at", sa.DateTime(timezone=True), nullable=True))
  ```
  `downgrade()` drops it under the same guard. Since the column is nullable with no default,
  adding it is a metadata-only change.
- `down_revision`: origin/main currently has **three** HRMS heads (`c3f8d21a9e47`,
  `f6bd834a55bb`, `d8a3f5c2b941`). `migrate.py upgrade heads` handles that. Chain onto
  `f6bd834a55bb` (it also touches user/role tables) and **don't** add a merge revision here,
  because that would be a separate decision.
