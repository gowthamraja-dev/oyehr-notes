## Database models — ONE FILE PER TABLE (Rails-style)

**When creating a new table, always create it as a separate model file.** Never put
multiple table classes in one file, and never reintroduce a combined `hr.py`.

1. Create `hrms/backend/app/models/<singular_snake_case>.py` (e.g. `department_master.py`)
   containing exactly one `class <PascalCase>(Base)` with `__tablename__ = "<plural>"`.
   - Filename is singular snake_case; `__tablename__` is plural (e.g. file `user.py`
     → class `User` → table `users`; file `employee_master.py` → `EmployeeMaster`
     → `employee_masters`).
2. **Register it**: add one import line to `hrms/backend/app/models/__init__.py`:
   `from app.models.<file> import <Class>  # noqa: F401`
   SQLAlchemy does NOT autoload like Rails — a model that isn't imported here is
   invisible to Alembic autogenerate and to the app.
3. Generate + review + apply the migration (see workflow below).

### Column conventions (match the existing four models)
- Primary key: `id: Mapped[int] = mapped_column(BigInteger, primary_key=True)`.
- Nullable columns: `Mapped[T | None]`; non-null: `Mapped[T]`.
- Non-null columns that have a default MUST use `server_default` (not just Python
  `default=`), e.g. booleans `server_default=text("true"/"false")`, ints `text("0")`,
  empty string `text("''")` — otherwise autogenerated `NOT NULL` columns reject inserts.
- Timestamps: `DateTime(timezone=True)`; `created_at` → `server_default=func.now()`,
  `updated_at` → also `onupdate=func.now()`.
- JSON columns: `from sqlalchemy.dialects.postgresql import JSONB`, typed `Mapped[Any | None]`.
- Foreign keys reference by table-name string: `ForeignKey("users.id")` — works across files.
- Reserved/builtin column names (`type`, `desc`): keep the DB column name but use a safe
  Python attribute, e.g. `org_type: Mapped[...] = mapped_column("type", ...)`.
- `*_master_id` fields whose master table doesn't exist yet → plain nullable `BigInteger`
  (add a real `ForeignKey` once that table exists).

## Migration workflow (Alembic)
Run from `hrms/backend/`. Never hand-edit an applied migration; create a new one.
```
uv run alembic revision --autogenerate -m "<message>"   # generate from models
# open alembic/versions/<new>.py and REVIEW it before applying
uv run alembic upgrade head                              # apply
```
After changing models, rebuild the API container so it runs the new code:
`docker compose up --build -d api`.

## Multi-tenancy — app-layer CDP scoping
Tenant boundary is `care_delivery_program_masters` (CDP), mirroring nh_server_app's
CDP model. The request subdomain resolves to one CDP via `organization_domain_mappings`
— a **polymorphic** table keyed by `(source_type, source_id)`, where `source_type =
'CareDeliveryProgramMaster'` today (the polymorphism leaves room to attach domains to
other sources later). A user's access is granted per `user_role_details` row via the
NOT-NULL FK `care_delivery_program_master_id`; the JWT carries that id as `tenant_id`.
There is **no Postgres RLS** on these tables — the database will NOT stop a cross-tenant
query. Every query touching tenant-scoped data MUST filter by the caller's CDP
(`user_role_details.care_delivery_program_master_id`). This is the highest-risk area for
data-leak bugs; add scoping at the service layer and cover it with tests.
(`organization_masters` was removed on 24-Jul-26; CDP replaced it as the tenant.)

## Authentication & sessions — stateless JWT bearer tokens
Login is tenant-scoped: the request subdomain resolves to a CDP, the user must hold an
active `user_role_details` membership in it, and a signed **HS256 JWT** (carrying `sub`,
`tenant_id`, `user_role_detail_id`, `role_master_id`, `is_admin`, `exp`) is minted. Every
later request authenticates on that bearer token ALONE — no server-side session store
(`hrms/backend/app/api/deps.py:get_current_principal`). Passwords are Argon2id. Full reference:
`hrms/docs/authentication-session-flow.md`. An optional login-OTP 2FA step (per-user, org-wide
toggle) can sit between password and a real session, using a short-lived narrowly-scoped
JWT (`get_current_principal` refuses it outside its one exchange endpoint).

**New authenticated endpoint** → depend on `CurrentPrincipal`/`CurrentUser` from
`app.api.deps`, and ALWAYS scope queries by `principal.tenant_id` (no RLS — the DB won't).
Cover the 401/403 and org-scoping cases in tests (see `hrms/backend/app/tests/modules/test_auth.py`).
Note the current gaps before relying on the flow in a higher-trust context: no token
revocation (logout just drops the client token), no refresh tokens, token lives in
`sessionStorage`, captcha is client-only, no login lockout — all documented in the doc above.

## Payload encryption — apply to new sensitive APIs and views
Request/response bodies on sensitive endpoints are encrypted (hybrid RSA-OAEP + per-request
AES-256-GCM), defense-in-depth on top of TLS. Full reference: `hrms/docs/payload-encryption.md`.

**New backend API that handles sensitive data** (auth, PII, anything org-scoped) → put it on
a router whose `route_class=EncryptedRoute`:
```python
from app.api.encryption import EncryptedRoute
router = APIRouter(prefix="/employees", route_class=EncryptedRoute)
```
Keep public/unauthenticated endpoints (branding, health, the `/public/crypto-key` endpoint
itself) as plain `APIRouter` — never encrypt them. Endpoints stay normal (Pydantic in/out);
the route class transparently decrypts the request and encrypts the response.

**New frontend call to an encrypted endpoint** → use `secureFetch` from `hrms/frontend/src/lib/crypto.ts`,
never raw `fetch`:
```ts
const { ok, status, data } = await secureFetch<T>("/api/v1/employees", { method: "POST", token, jsonBody });
```
Calls to plaintext/public endpoints keep using plain `fetch` (see `getOrganization`).

**Don't forget:** CORS must keep `expose_headers=["X-Encrypted"]` in `hrms/backend/app/main.py` (browsers
hide it otherwise → client can't decrypt). WebCrypto needs a secure context (`localhost`/
`https`). Errors return plaintext by design. Add an encrypted round-trip test like
`hrms/backend/app/tests/modules/test_encryption.py` for new encrypted routers.

## Logging & observability — structlog over stdlib, one pipeline
Full references: `hrms/docs/logging.md` and `hrms/docs/observability.md` (in workspace-2 since
13-Oct-26, branch `feature/gowtham_Observability`; the top-level `hrms/` clone still has the
older stdlib-only setup until that branch is merged and pulled). structlog was adopted
app-wide by explicit decision. It renders through stdlib handlers, so there is ONE pipeline
(`hrms/backend/app/observability/logging_config.py`). Don't add another logging library.

```python
import structlog
logger = structlog.get_logger(__name__)
logger.info("shift_created", shift_id=shift.id)
```

**New files** → `structlog.get_logger(__name__)`, snake_case event names, ids as fields.
Existing `logging.getLogger(__name__)` + `%s` calls keep working (same JSON output). INFO on
state-changing success, WARNING at the guard that raises, `logger.exception(...)` in `except`.
Never log PII, credentials, bodies or SQL parameters. `request_id`/`tenant_id`/`user_id` are
attached automatically. `LOG_FORMAT=json` in deployed images. Every response carries
`X-Request-ID`. Probes: `/livez` (liveness, no I/O), `/readyz` (DB). Prometheus metrics are on
`METRICS_PORT` 9100, never the API port. Local monitoring stack:
`docker compose -f monitoring/compose.yaml up -d --build` from `workspace-2/hrms/`
(project `hrms-ws2-obs`).

## Cloud setup (AWS) — build new work to fit this
Production runs on: **RDS** (PostgreSQL, managed) · **ECS Fargate** (backend Docker image
from ECR, behind an ALB) · **AWS Amplify** (the Next.js frontend). Local dev is still Docker
Compose. Full setup + must-dos: `hrms/docs/deployment-aws.md`. Write every new feature so it works
under this without change:

- **Config only via env / `Settings`** — never hardcode secrets, hosts, URLs, or keys.
  In prod these come from the one Secrets Manager JSON secret `hrms/prod` (`DATABASE_URL`,
  `SECRET_KEY`, `CRYPTO_PRIVATE_KEY`, `CORS_ORIGINS`, …), loaded by the app at startup when
  the image sets `SECRETS_PROVIDER=aws` (dev k8s image: `SECRETS_PROVIDER=k8s`; unset locally).
  Add any new secret as a `Settings` field. Reference: `hrms/docs/secrets-config.md`.
- **Stateless, ephemeral containers** — Fargate tasks have no persistent local disk and run
  as N replicas. Do NOT rely on local files or in-process state that must survive/scale
  (the dev `.crypto_key.pem` is dev-only; prod injects a shared `CRYPTO_PRIVATE_KEY`).
  Shared state goes to **RDS**, **ElastiCache/Redis**, or **S3** — not the container.
- **HTTPS is required in prod** (WebCrypto `crypto.subtle` — hence payload encryption —
  only works in a secure context). Assume TLS is terminated upstream (ALB/CloudFront/Amplify).
- **Multi-tenant subdomains** resolve via `organization_domain_mappings.host`; prod uses a
  wildcard domain + cert. Don't assume a single fixed host.
- **New backend service** → containerize (reuse `hrms/backend/Dockerfile`), deploy on ECS.
  **New frontend** → stays inside the Amplify Next app. Set `NEXT_PUBLIC_API_URL` via env.
- **Migrations** run as a controlled one-off step in the deploy pipeline, not racily on every
  task boot. Never hand-edit an applied migration (see the Alembic workflow above).

## File uploads — always use the shared image service

**Never duplicate file-upload logic.** Any feature that stores a file in S3 and tracks it
in `image_details` MUST use `hrms/backend/app/services/image_service.upload_image()`:

```python
from app.services import image_service

row = image_service.upload_image(
    db,
    user_id=current_user.id,
    imageable_type="EmployeeMaster",   # polymorphic entity type
    imageable_id=employee.id,
    file_bytes=raw_bytes,
    content_type=file.content_type,
    img_type="profile",                # stable string key, e.g. "logo", "profile", "cert_gst"
)
# row is an ImageDetail ORM instance — convert to your response schema as needed
```

The service handles: size validation (default 1 MB), MIME-type validation, S3 upload
(`{env}/{ folder}/{entity_id}/{img_type}/{epoch}.{ext}`), deactivating the previous active
row for the same `(imageable_type, imageable_id, img_type)`, and inserting the new row.

`imageable_type` → S3 folder mapping lives in `_FOLDER` inside `image_service.py`; add an
entry there when introducing a new entity type (e.g. `"PatientMaster": "patient"`).

**Frontend**: for multipart uploads use plain `fetch` (not `secureFetch`) because
`EncryptedRoute` doesn't support multipart. Use a plain `APIRouter` on the backend side
for file endpoints (same pattern as `_upload_router` in `organizations/router.py`).

**img_type values in use** (update this list as new types are added):

| Entity | img_type | Description |
|---|---|---|
| CDP | `logo` | Organisation sidebar logo |
| CDP | `favicon` | Browser tab icon |
| CDP | `cert_incorporation` | Certificate of Incorporation |
| CDP | `cert_gst` | GST Registration Certificate |
| CDP | `doc_pan` | Company PAN Card |
| CDP | `doc_bank_proof` | Cancelled Cheque / Bank Proof |
| CDP | `doc_address_proof` | Registered Address Proof |

## Dynamic forms — the `nhforms` package

Forms are **not** built in HRMS. They come from the installed `nhforms` package
(backend `nhforms`, frontend `@nanohealth/nhforms`), published to AWS
CodeArtifact from `../nhforms`. HRMS only hosts it.

**What HRMS owns** (`hrms/backend/app/modules/forms/`):

| File | Role |
| --- | --- |
| `registry.py` | Receives what the package contributes (routes, permissions, events, migrations) |
| `deps.py` | The two dependencies the package requires: the async session/principal context and the permission gate |
| `router.py` | Installs `NHFormsModule` and mounts it at `/api/v1/forms` |

Everything under `/api/v1/forms` is served by the package — do not add form
endpoints to HRMS.

### Two things that differ from the rest of HRMS

1. **nhforms is async; HRMS is sync.** `hrms/backend/app/core/db.py` therefore has a *second*
   engine — `async_engine` / `AsyncSessionLocal` / `get_async_db` — reusing the
   same `DATABASE_URL` (psycopg3 drives both). SQLAlchemy's async layer needs
   `greenlet`, which is an explicit dependency for that reason. HRMS routes keep
   using the sync session.
2. **Migrations must run through `hrms/backend/scripts/migrate.py`.** The package ships its own
   Alembic branch, so there are two heads *and* its revisions live inside the
   virtualenv. A bare `alembic upgrade head` fails on the ambiguity and cannot see
   the package's revisions at all:

   ```bash
   uv run python hrms/backend/scripts/migrate.py upgrade heads   # not `alembic upgrade head`
   ```

   `alembic/env.py` still merges the package's metadata so autogenerate never
   emits a DROP for its tables.

### Installing / upgrading the package

The CodeArtifact token is short-lived (≤12h), so mint one first — for `uv add`,
and for **any Docker build**, since the image installs `nhforms` from the private
index (passed as a BuildKit secret, never a layer):

```bash
export CODEARTIFACT_AUTH_TOKEN="$(aws codeartifact get-authorization-token \
  --domain nhforms --domain-owner 431176070080 --region ap-south-1 \
  --query authorizationToken --output text)"
export UV_INDEX_CODEARTIFACT_USERNAME=aws UV_INDEX_CODEARTIFACT_PASSWORD="$CODEARTIFACT_AUTH_TOKEN"

uv add nhforms==<version>
docker compose up --build -d api
```

### Seeding a form

The tables are created empty and the package's form *builder* is not finished, so
form definitions come from the legacy Rails MySQL database:

```bash
uv run python hrms/backend/scripts/seed_nhforms_form.py 3595
```

It copies one form plus everything it references, and sets the two columns that
exist only in nhforms — `reference_type` / `reference_srce` — which decide what a
submitted response attaches to. For form 3595 that is
`('EmployeeMaster', 'employee_master_id')`, so a response is stored against the
employee whose id the submit payload carries under that key. Add new forms to
`REFERENCE_BY_FORM` in the script.

### The shared-link flow

`hrms/frontend/src/app/forms/[formId]/page.tsx` — `/forms/3595?employee_master_id=38`.
Standalone and unauthenticated by design: HR emails the link, the employee opens
it, fills the form and submits. The form id comes from the path, the employee id
from the query, and the backend only honours the latter because the form is
configured for it.

The success popup after submit is the package's, configured by the form's own
`form_parameter_masters` rows (134 message / 133 redirect); a form with neither
gets a default confirmation.

### "Add Employee" is a form submission — EMPFN/EMPMB are load-bearing

There is no separate HRMS-native employee-creation endpoint. `GET /employees/add-form`
(`hrms/backend/app/modules/employees/service.py:get_add_employee_form_id`) resolves which
`form_type_master_id = 10` (Registration) form the "Add employee" button opens, and
submitting it is what creates the `EmployeeMaster` row — the nhforms package does this
itself, keyed off two hard-coded question codes it looks for in the answers: `EMPFN`
(First Name) and `EMPMB` (Mobile) — see `nhforms/core/constants.py: REQUIRED_CODES`,
enforced in `nhforms/registration.py: guard_duplicates`.

This contract is **invisible to the Form Designer**: nothing stops an admin from
hiding, deactivating, or replacing the EMPFN/EMPLN mapping on a Registration form
through the builder UI, and the failure that results has no field-attributed error —
the rejection logic only reports errors for mapping ids that were actually submitted,
so a hidden/inactive field just produces a bare "employee cannot be added" with
nothing to point at. **When building or editing a Registration-type form, never
deactivate/hide/replace the mapping rows carrying question codes `EMPFN` or `EMPMB`** —
check the question's `questn_code` (via `field_type_masters`/`questnr_masters`), not
just its label, since multiple questions can share a label like "First Name" while
only one carries the code the backend actually requires.

## Roles & Permissions (RBAC) — one screen owns the policy tables

`policy_masters` / `policy_statements` / `policy_mappings` are written by exactly one
place: the HR Admin → Roles & Permissions screen (`/api/v1/roles/admin/*`,
`hrms/backend/app/modules/roles/`). Full reference: `hrms/docs/roles-and-permissions.md` (end-to-end: storage, evaluation, every gated endpoint, scenarios, runbook).

- **Roles are GLOBAL** (`role_masters` has no CDP column). Membership
  (`user_role_details`), permission grids and overrides are all CDP-scoped — so
  every query about *who holds a role* filters on `principal.tenant_id`.
- **The grid is declared once**, in `hrms/backend/app/modules/roles/permissions.py` (resources ×
  actions + which pairs are applicable). Add a module there, not in the frontend.
  Stored verbs are `READ/CREATE/UPDATE/DELETE/APPROVE`; the UI labels READ as "VIEW"
  and UPDATE as "EDIT", and the label ships with the action.
- **Never widen a statement delete beyond the grid.** The same policy can carry
  `ROLE`/`POLICY`/`LEAVE_REQUEST` statements the screen doesn't show.
- **Per-employee overrides store only the diff** against the role (ALLOW/DENY), which
  is what makes them survive later role changes.
- **Creating a role requires a dashboard.** `role_masters` is global, so new roles are
  tagged `parameter_detail = {"created_for_cdp_id": <cdp>}` and hidden from other
  tenants. Dashboard options exclude the Super Admin portal and are filtered client-side
  through `SUPPORTED_DASHBOARD_PATHS` in `hrms/frontend/src/dashboards/registry.ts` — a path
  with no loader renders a blank shell.
- **Any code that creates a `user_role_details` row MUST set `dashboard_master_id`.**
  Login puts it in the JWT and the shell renders the entire app from it — a row
  without it logs in to a blank dashboard. Resolve it with
  `app.modules.roles.service.resolve_dashboard_id` (role pointer → what existing
  holders in the CDP use → a dashboard named after the role) and refuse the write
  if nothing resolves.
- **Gate new endpoints** with `RequirePermission("<ACTION>", "<RESOURCE>")` from
  `app.api.authz` (route dependency) or `assert_permission(db, principal, …)` in a
  service. Leave self-service routes (a caller's own record) ungated.
- **Unconfigured roles are unrestricted.** A role with no saved grid passes every
  check (`configured=False`), so adding a gate cannot lock out a tenant that has not
  set RBAC up; the screen shows an explicit banner for both states. Overrides beat the
  role, `DENY` beats `ALLOW`, Super Admin bypasses.
- **Anything that creates data inside an nhforms submission is gated in
  `hrms/backend/app/modules/forms/authz.py`**, not in nhforms' `permission_checker` — the package's
  submission routes inject that hook and never call it. A Registration-form submit is
  checked as `CREATE EMPLOYEE`, because that is what creates an employee.
- **Default grids for HR Admin / HR Manager / Employee** live in
  `hrms/backend/app/modules/roles/defaults.py` (the signed-off design). Apply them with
  `hrms/backend/scripts/seed_rbac_defaults.py --cdp <id>` or the screen's "Apply default
  permissions" button — never automatically on boot, since seeding is what switches a
  tenant on to enforcement. Where a module can do something the grid has no cell for
  (Attendance/Settings deletes), gate it on the nearest cell (`UPDATE`), never leave it
  ungated.
- Cover new gates in `hrms/backend/app/tests/modules/test_authz.py`.
- **Never hand-delete from the policy tables.** `hrms/backend/scripts/cleanup_policy_data.py` finds the
  known kinds of stale rows, writes every row it will delete (plus cascaded children) to a
  JSON backup outside the DB, and can restore from that file. Dry run by default; `--apply`
  to write. Deactivated policies and overrides for inactive memberships are deliberate
  states and are NOT swept by default.

## File imports — the staged import engine, attendance first
Bulk "upload a CSV/XLSX" features run on one engine (`hrms/backend/app/modules/file_import/`, tables `import_batches` /
`import_field_mappings` / `import_rows`): the upload only stores rows; validation, commit and settling run in a
resumable background runner (heartbeat claim, per-chunk commits, a 5-minute `file_import_resume` job, 30-day
scratch-row retention). A new import type is one `ImportHandler` + one grid row + one frontend config — **never a new
table family or runner**. Every route is gated by `require_grid_permission` on the handler's own grid row (a role with
no saved grid is refused) and filtered by tenant AND `import_type`. Full reference: `hrms/docs/file-import.md`.

**Attendance bulk import** (`hrms/backend/app/modules/attendance_import/`, `/api/v1/attendance-import`, grid row `ATTENDANCE_IMPORT`):
one row = one employee-day, with or without In/Out times (no times = present for the scheduled shift). It writes raw
`Import` punches and lets `recompute_attendance_day` derive the day — never `employee_attendance_details` directly.
Locked days need org-wide scope + a reason; imports can be undone. Full reference: `hrms/docs/attendance-bulk-import.md`.

## File exports — the shared export engine
Every "download as CSV / XLSX" feature runs on one engine (`hrms/backend/app/modules/file_export/`): a report type is one `ExportHandler`
(params model + `build` returning an `ExportTable`) and the engine owns the route, the READ gate, the cell limit (250,000), CSV
(UTF-8 BOM) and XLSX writers, the `'` formula-injection guard, the filename and the audit hook — **never a new endpoint family or a
second CSV writer**. Exports are stateless: no tables, no runner, no migration. Plain `APIRouter` (binary body; `EncryptedRoute` can't
carry it) and plain `fetch` on the frontend (`getExportCatalogue` / `downloadExport`), driven by `FileExportDialog`. Handlers must scope by
`principal.tenant_id`. Full reference: `hrms/docs/file-export.md`.

**Attendance reports** (`hrms/backend/app/modules/attendance_export/`, `/api/v1/attendance-export`, `ATTENDANCE` READ): `attendance_ledger` (employee rows x date
columns, status codes), `hours_ledger`, `monthly_summary`, `daily_log` — all read the register's own employee-day rows, so scope and status rules match the screen.
`/attendance/register/export` is the `daily_log` builder in its original shape and must stay byte-identical (golden files in `hrms/backend/app/tests/golden/`).
Full reference: `hrms/docs/attendance-export.md`.

## Testing — every module ships with tests
Every backend module MUST have tests under `hrms/backend/app/tests/modules/test_<module>.py`, run with
`uv run pytest`. Use the shared fixtures in `hrms/backend/app/tests/conftest.py` (transactional rollback
session, `client`, `tenant`, `user`, …); follow `test_auth.py` / `test_public.py` /
`test_encryption.py`. Cover the happy path, auth/permission failures, **org-scoping**
(never leak across tenants), and validation errors. Encrypted routers also get an encrypted
round-trip test. Add tests in the same change as the feature — not later.

## Documentation — write a doc for any non-standard flow
When you introduce a flow or setup that isn't obvious from the code (a new auth/crypto scheme,
an external integration, a deployment/infra step, a cross-cutting pattern), add a Markdown doc
under `hrms/docs/` explaining what it is, how it works, and how to set it up elsewhere — like
`hrms/docs/payload-encryption.md`. Link it from the relevant CLAUDE.md section. Routine CRUD
modules that follow existing conventions don't need their own doc.

## Frontend styling — Tailwind CSS only

The project uses **Tailwind CSS v4** (`@import "tailwindcss"` in `hrms/frontend/src/app/globals.css`).

- **All styling must use Tailwind utility classes.** Never create new `.module.css` files.
- **Exception — DB-driven values only:** use CSS custom properties (defined in `globals.css`)
  or inline `style={{}}` when the value will be fetched from the database at runtime
  (e.g. `--brand-gradient`, org-specific accent colors). Everything else is Tailwind.
- Custom design tokens (teal palette, ink palette, app-bg, border colors) live in the
  `@theme {}` block in `globals.css` so they are available as `bg-teal-950`,
  `text-ink-500`, etc.
- Responsive variants, hover, focus states → standard Tailwind modifiers
  (`hover:`, `focus:`, `max-[1000px]:`, etc.)
- `@keyframes` needed by Tailwind's `animate-*` utilities go in `globals.css`.

## Loading states — shimmer skeletons

Never use plain "Loading…" text or a centred spinner for page-level loading states.
Instead, render a **shimmer skeleton** that mirrors the real layout structure — think
of it as "the UI before the data arrives," not a random collection of grey rectangles.

**Always compose skeletons from the shared primitives** in
`hrms/frontend/src/components/ui/Shimmer.tsx` (`Shimmer`, `ShimmerLine`, `ShimmerAvatar`,
`ShimmerPill`, `ShimmerButton`, `ShimmerRow`, `ShimmerList`, `ShimmerCard`,
`ShimmerMetricTile`/`ShimmerMetricTileRow`, `ShimmerTable`, `ShimmerFilterBar`,
`ShimmerTabs`, `ShimmerPageHeader`, `ShimmerForm`, `ShimmerChart`, `ShimmerBrandHeader`) —
never hand-roll a new `animate-pulse` block. They all render on top of the shared
`.shimmer` / `.shimmer-dark` / `.shimmer-dark-strong` classes (see "Frontend styling"
above); pick `tone="dark"`/`"dark-strong"` only inside the dark dashboard rail, `"light"`
(the default) everywhere else. The **one sanctioned exception** is a DB-driven value that
isn't known yet (e.g. the org's brand color on login/reset-password) — use
`ShimmerBrandHeader` or the same `color-mix(in srgb, var(--brand-primary) …%, white)`
inline-style pattern, per the "Frontend styling" DB-driven-value exception; nowhere else.

Rules that keep every page's skeleton faithful to its real layout:

- **Match structure, not just a bounding box.** A metric tile is icon-chip + value-line +
  label-line (`ShimmerMetricTile`), never one flat block; a table is always a header row
  (one line per real column) + N body rows with the *same* `gridTemplateColumns`
  (`ShimmerTable`) — dropping the header row is the most common regression to watch for.
- **Never fabricate an element the real page doesn't have** (an invented title, a section
  that only appears once data loads) — that guarantees a layout-shift bug the moment real
  content mounts. Read the real component before writing its skeleton.
- **Never hardcode a count that's genuinely dynamic** (action columns, filter pills) —
  take it as a prop from the same source the real render uses, or a documented fixed
  constant (e.g. the RBAC grid's 5 stored verbs, see hrms/CLAUDE.md's "Roles & Permissions").
- **Modals**: keep the header/footer chrome (`px-5 py-4`) real and static; only the
  scrollable body swaps to a skeleton.
- Match the real page's own padding/gap/radius exactly — read them off the real JSX,
  don't assume the 10px page-spacing convention already applies (see `hrms-spacing` skill;
  many older pages still predate it).
- Export the skeleton as a named component alongside the real component
  (e.g. `DashboardSkeleton` exported from `shell.tsx` next to `DashboardShell`).
- The page loader (`dashboard/page.tsx`) returns the skeleton while data loads,
  then swaps in the real shell — no layout shift.
- Do NOT block the whole page on data; show the skeleton immediately and let
  the data fetch run in the background.
